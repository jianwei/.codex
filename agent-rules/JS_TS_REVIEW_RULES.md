# JavaScript 与 TypeScript 代码评审规则

本文件是 JavaScript 与 TypeScript 评审的补充层，适用于 `.js`、`.jsx`、`.mjs`、`.cjs`、`.ts`、`.tsx`、`.mts`、`.cts`，以及 Vue 单文件组件中的 `<script>`、`<script setup>` 和模板表达式调用的脚本逻辑。执行评审时必须同时读取 [JavaScript 与 TypeScript 代码规范](/Users/chenjianwei2/.codex/agent-rules/JS_TS_CODE_RULES.md) 和 [代码评审与工程约束](/Users/chenjianwei2/.codex/agent-rules/CODE_REVIEW_RULES.md)；本文件只规定 JS/TS 评审方法和输出合同，不重复两份基础规则。Vue 模板结构与 HTML 语义另按 [HTML 代码规范](/Users/chenjianwei2/.codex/agent-rules/HTML_CODE_RULES.md) 评审。

## 1. 确认评审边界与证据

- 先确认比较基线、实际 diff、未跟踪文件和生成文件，区分本次新增缺陷、既有问题与不在评审范围的代码；finding 只报告本次变更新增或使其可触发的问题。
- 从修改点沿真实调用链检查入口、参数来源、状态写入、异步边界、返回值和最终副作用；公共导出、共享类型、配置、路由或请求合同发生变化时，检索所有调用方和消费者，不能只看当前文件。
- 以源码、类型检查、测试、构建结果或可复现运行行为作为证据。无法证明触发条件或影响时继续核对，不把偏好、猜测和纯格式差异写成 finding。
- 项目已有 lint、类型、测试和构建配置是评审基线；规则冲突时先确认项目与运行环境合同，再判断是否构成问题。

## 2. 运行时与模块边界

- 核对浏览器、Node、SSR、WebView、Worker 和旧运行时等实际目标；检查新语法、API、全局对象、模块顶层副作用及 ESM/CommonJS 互操作在目标环境中是否成立。
- 检查导入路径、包公共入口、循环依赖、默认与命名导出、类型导入和 tree shaking 行为；确认新增依赖声明在正确包中，且不会把服务端模块带入浏览器或反向引入。
- 公共函数、共享模型、事件、存储、URL、请求与响应结构的变化必须兼容真实消费者；字段重命名、可选性和默认值变化要沿序列化与反序列化链核对。

## 3. TypeScript 类型安全

- 检查 `any`、双重断言、非空断言、过宽索引签名和不真实的可选字段是否掩盖运行时缺口；外部数据和捕获异常应从 `unknown` 开始，经运行时证据收窄。
- 检查可辨识联合、泛型约束、重载、类型守卫、穷尽分支和公开返回类型是否表达真实合同；不能让类型声明比运行时数据更窄或更乐观。
- 检查 JavaScript 的 JSDoc 类型是否与实现一致，并确认类型导入不会产生意外运行时依赖。

## 4. 控制流与数据语义

- 逐条核对成功、失败、空值、零值、取消、重试、重复触发和状态切换分支；区分 `null`、`undefined`、空字符串、零、空集合和缺失字段的业务含义。
- 检查边界归一化、数字与日期解析、单位、时区、精度、枚举和值域；不能依赖宽松相等、隐式转换或真值判断改变协议语义。
- 检查提前返回、条件优先级、短路表达式、闭包捕获和对象展开是否遗漏副作用或传播无关字段；修改输入对象、共享引用或缓存时确认所有权与失效策略。

## 5. 异步、并发与资源清理

- 每个 Promise 必须被等待、返回、组合或明确处理；检查竞争条件、乱序响应、重复提交、并发去重、失败回滚和取消传播。
- timer、listener、observer、subscription、AbortController、对象 URL、轮询和动画帧必须有对称清理；组件卸载、路由切换、超时、失败和取消路径均不能遗留资源或继续写状态。
- 手写 Promise 与回调桥接须保证成功、错误、超时和取消只 settle 一次；`finally` 不得覆盖原返回值或错误。

## 6. 错误处理与安全

- `catch` 必须区分可恢复错误、约定取消和真实故障；不得吞掉需要反馈、重试或观测的失败，也不得用通用成功值掩盖异常。
- 检查错误转换是否保留状态码、业务码、cause 和必要上下文，同时避免将令牌、Cookie、个人信息或响应正文泄露到日志与用户界面。
- 所有不可信输入在进入 HTML、URL、路径、命令、存储键、正则、跨窗口消息或动态属性前须按目标语境校验或转义；检查开放重定向、原型污染、路径遍历、注入和越权调用。
- 身份认证、权限、功能开关和环境判断必须在可信边界执行；前端隐藏入口不能替代服务端授权。

## 7. 性能与可维护性

- 只对可触发的热点报告性能问题；检查大集合中的重复遍历、循环内线性查找、无界缓存、重复序列化、重复请求、渲染期副作用和未受控并发。
- 评估新增依赖、动态导入和模块副作用对包体积、首屏与服务端启动的实际影响；没有测量或明确规模依据时不做微优化 finding。
- 检查同一状态或协议是否产生第二个真源，新增抽象是否确有多个消费者；评审修复方向应保持最小，不借机重构无关代码。

## 8. 测试与工具验证

- 根据变更合同检查关键正向路径，以及可触发的失败、空值、边界、取消、并发和兼容路径；测试必须执行真实逻辑，并在目标缺失时明确失败。
- 类型层问题运行项目既有类型检查，语法与质量问题运行 lint，行为问题运行相关单元或集成测试，打包与运行时边界变化运行生产构建或目标环境验证。
- 不把工具通过当作行为正确的充分证据，也不把未运行的命令写成已通过。工具无法运行时记录原因，并基于可获得证据限定结论。
- 测试文件布局遵循 [测试目录布局](/Users/chenjianwei2/.codex/agent-rules/TEST_LAYOUT_RULES.md)，但目录或命名偏差只有在本次变更引入且违反生效规则时才作为 finding。

## 9. Finding 输出标准

- finding 按严重性从高到低排序；同一根因合并，优先报告会导致错误行为、安全问题、数据损坏、兼容失败或明显回归的事项。
- 每条 finding 必须包含：严重性与简短标题、文件和精确行号、可复现的触发条件、实际影响、最小修复方向。行号应落在本次 diff 或能直接说明问题的最小范围。
- finding 必须说明为什么现有实现会失败，避免只复述规则；若影响取决于外部合同，指出已核对的合同证据或明确尚缺的证据。
- finding 之后可简要列出已执行的验证和剩余验证边界。没有可执行问题时明确输出“未发现问题”，并说明已检查范围及未覆盖的运行环境或测试限制。

建议格式：

```text
[P1] 标题 — path/to/file.ts:42
触发条件：……
影响：……
修复方向：……
```
