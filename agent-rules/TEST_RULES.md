# 测试规则

新增、迁移、修改或评审测试文件与测试用例时，遵循本文件。

## 测试目录布局

- 所有测试代码放在项目根目录的 `__tests__/` 中。
- `__tests__/` 内的目录路径镜像被测试代码相对项目根目录的目录路径。例如，被测试文件为 `src/services/user.ts` 时，测试文件放在 `__tests__/src/services/` 中。
- 测试文件名保留项目现有的测试后缀和命名约定，仅统一测试代码所在目录。

## 用例描述完整性

测试用例应在不虚构需求的前提下尽可能详细，使未参与开发的人也能按照用例独立执行并判断结果。

- 每个用例应明确记录：用例编号、功能模块、测试标题、测试目的、优先级、测试类型、关联需求或缺陷、前置条件、测试数据、操作步骤、逐步预期结果、最终预期结果和清理或恢复方式。
- 前置条件应写明账号角色、权限、环境、配置、初始数据、页面或接口入口以及依赖服务状态，不能只写“环境正常”“准备数据”等无法复现的描述。
- 测试数据应给出具体字段、取值、数据状态和数据之间的关系；敏感信息使用明确的脱敏占位值。
- 操作步骤按实际执行顺序编号，每一步只包含一个主要动作，并写清操作对象、输入内容、触发方式和必要的等待条件。
- 每个关键步骤都应有对应的可观察预期，写清页面文案、字段值、状态变化、接口请求、响应、跳转、持久化结果或副作用，避免只在末尾写“结果正确”。
- 最终预期应明确成功或失败的判定标准；存在数据库、缓存、消息、日志或下游调用影响时，写明需要核对的最终状态。
- 用例依赖其他用例或公共准备步骤时，必须明确引用；测试用例仍需具备可独立理解和复现所需的信息。
- 自动化测试无法容纳完整背景时，在测试名称、分组、Fixture 名称和必要注释中保留关键条件与预期，并关联对应的需求、缺陷或测试用例编号。

## 测试范围

- 测试应验证对用户、调用方或系统合同可观察的行为，优先覆盖业务规则、接口合同、状态转换和回归风险。
- 选择能够证明行为的最小测试层级：纯逻辑使用单元测试，模块协作使用集成或合同测试，完整用户流程和浏览器差异使用端到端测试。
- 不为可逆、低影响的改动机械补测试，也不编写只复述实现细节的测试。
- 修复缺陷时，应添加能够在修复前失败、修复后通过的回归用例。

## 场景设计

- 每个受影响的独立条件分支至少有一个直接命中的正向用例。
- 除成功路径外，按实际风险覆盖失败、缺失、空值、非法值、边界值、未知值、取消、重试、并发和状态切换；不为实际不可达的分支凑数量。
- 对输入范围、角色权限、业务状态、终端或浏览器、网络状态、时间条件和依赖响应进行等价类与边界分析，并明确哪些组合需要单独用例。
- 涉及流程时覆盖正常进入、前进、返回、刷新、中断、恢复、重复提交和完成后的再次访问；不适用的场景应有事实依据。
- 用例名称明确写出条件、行为和预期结果，使失败信息可以直接定位问题。
- 每个用例只验证一个核心行为；准备数据保持最小，避免依赖隐式的共享前置状态。

## 断言要求

- 断言返回值、状态、外部调用、渲染结果、可访问语义等可观察结果，避免断言私有实现、源码文本或正则匹配代码结构。
- 操作目标或前置数据必须先断言存在且唯一；不得用可选链等方式静默跳过关键交互或断言。
- 只有完整且稳定的输出本身就是合同的一部分时才使用快照；其他场景优先使用精确的语义断言。
- 不得通过删除断言、放宽预期、添加 `skip` 或 `only`、无依据更新快照来使测试通过。

## Mock 与测试数据

- Mock 应放在最窄的合同边界，保留被测路径中的真实逻辑；需要替换共享模块时优先使用部分 Mock。
- 不 Mock 被测对象自身。纯函数、数据转换和可控依赖优先使用真实实现。
- 接口 Mock 应保持真实的状态码、响应结构和业务成功条件，避免用失真的固定成功数据掩盖失败路径。
- Fixture 仅保留当前场景所需字段，使用虚构或脱敏数据，不写入生产凭据和个人敏感信息。

## 异步与隔离

- 等待可观察条件或使用框架提供的异步工具；时间相关逻辑使用可控时钟，不使用任意时长的休眠。
- 每个用例创建独立的路由、状态容器、查询客户端、事件总线或其他可变依赖。
- 用例结束后恢复全局对象、定时器、DOM、网络 Mock 和环境变量；测试应能单独运行，且不依赖执行顺序。

## 测试基础设施

- 测试、helper 和子进程基于 `import.meta.url`、项目根配置或测试运行器提供的根目录推导路径，不硬编码开发者主目录、盘符或工作区绝对路径；验证从任意工作目录、CI checkout 和包含空格或非 ASCII 字符的路径启动时仍能定位同一资源。
- 浏览器全局对象、运行时配置、Cookie 和公共环境变量通过唯一共享 setup 或 helper 建立基础合同，用例只覆盖自身差异并在结束后恢复，避免各文件复制出不一致的浏览器环境。自定义 loader 或别名解析器使用 `URL`、`fileURLToPath`、`path` 等结构化 API 解析与拼接，显式区分 URL 编码和文件系统路径，并识别调用方已提供的合法扩展名；测试覆盖空格、中文、百分号、查询或片段、已有扩展名、不同导入上下文以及无法解析时的明确失败。

## 执行与证据

- 使用项目已有测试脚本，先运行受影响的定向测试，再按风险运行类型检查、静态检查或更大范围测试。
- 如实记录实际执行的命令和结果，不得把未运行的测试、CI 或人工验证描述为已通过。
- 实施和评审同时遵循 [代码评审与工程约束](/Users/chenjianwei2/.codex/agent-rules/CODE_REVIEW_RULES.md)。
